0001-input-eswin-eph861x-wait-for-reset-report-in-probe.patch
  eph_probe() slept a fixed msleep(5000) "wait ic boot done" after enabling
  the regulators. The IC sends its reset device-state report ~170 ms after
  power-on (kernel6 dmesg: regulator enable 1.257 s, "Reset completed"
  1.427 s), and the IRQ thread already completes ephdata->reset_completion.
  The patch waits for that completion, then a 50 ms settle delay. If no
  report comes, it falls back to the old 5 s, counted from regulator enable.
  Parameters of the built-in driver (kernel command line):
    eswin_ts.ic_boot_timeout_ms=5000   upper bound (old fixed delay)
    eswin_ts.ic_boot_settle_ms=50      set to 5000 for the old behaviour

0003-input-eswin-eph861x-no-stale-chg-reads-report-gesture-errors.patch
  (2026-10-27; touch at idle display-off)
  Symptom on kernel6: every idle display-off logs ESWIN SPI read errors
  ("No response type: 255" / "Failed to read header: (-5)" / "Failed to read
  message (-5)") and fp6-lomiri-powerd sometimes logs "touch lp_mode change
  failed: [Errno 16]".
  Cause (code reading): the CHG IRQ thread waits on comms_mutex while a
  synchronous command (eph_write_control_config) reads its own response,
  then reads the already-consumed message -> 0xff. LP entry sends two
  commands, so two error triads per display-off (same triad during probe).
  EBUSY from lp_mode = gesture_wakeup_enable clear: the gesture_wakeup store
  returned success even when its controller command failed.
  The patch: IRQ thread skips the read when CHG is no longer asserted (not in
  bootloader); gesture_wakeup store returns the command error and takes
  lp_lock; lp_mode logs which condition was busy.
  powerd (sensors/fp6-lomiri-powerd.py) already copes without it: LP before
  blank, non-blocking retry with backoff that re-selects double tap.
  Apply AFTER ../sensors/0003 and 0001 above.
  Compile check (W=1, no warnings in eswin_eph861x.c): eswin-lp-compile-check.nix ->
    /nix/store/dzb5c90x2hbl5xl01i7h71xsdhqja936-fp6-kernel7-candidate-eswin-lp-compile-check-63289f441152-nixos6

0004-drm-msm-a8xx-invalidate-cche-on-pagetable-switch.patch
  (white-boxes investigation, 2026-10-27; UNVERIFIED candidate, not upstream)
  a6xx_set_pagetable() ends a context switch with CACHE_INVALIDATE only. On
  gen8 Mesa and turnip emit CP_CCHE_INVALIDATE in addition to that event,
  which suggests the event does not cover the CCHE. The patch adds
  WFI + CP_CCHE_INVALIDATE after it on a8xx, so no context samples lines
  cached under the previous pagetable. Target symptom: glyph atlases in the
  shell and several apps turning into solid boxes at once (memory fine, no GPU
  fault logged, logout cures it). Two extra dwords per context switch.
  Touches only drivers/gpu/drm/msm/adreno/a6xx_gpu.c; applies to the 7.2
  tree (patch --dry-run). Not compile-checked (needs an in-tree msm build).
  Test plan: only after the Mesa backport
  (nixos-fp6/feature-push/white-boxes) and msm.enable_preemption=0 have
  been tried, because this needs a full kernel7 build and module re-pinning.
