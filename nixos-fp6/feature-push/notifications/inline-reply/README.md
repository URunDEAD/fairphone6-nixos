# Inline replies for notifications (Lomiri, FP6)

Roadmap item "Notification quick replies beyond SMS", 2026-10-28.
Module: `inline-reply-fp6.nix` (`hardware.fairphone6.inlineReply.enable`,
default on), imported by `trial-lomiri-full-kernel6-fp6.nix`.

Before this, the only quick reply on Lomiri was for SMS. telephony-service
puts each message into the messaging indicator (ayatana messaging menu) with a
text-field action. The notification bubbles had no reply, and the Lomiri
notification server dropped the actions of ordinary (ephemeral)
notifications. The SMS path is unchanged.

## What it does

Apps that use the freedesktop/KDE inline-reply convention now get a reply
field. That includes Telegram Desktop, KDE apps through KNotification
(NeoChat, ...) and anything that checks `GetCapabilities` for
`inline-reply`:

* **Server** (`lomiri-notifications-inline-reply.patch`, C++, on top of
  notifications' `lomiri-notifications-app-name.patch`):
  * `GetCapabilities` lists `inline-reply`.
  * A `Notify` whose actions contain `"inline-reply", <label>` gets the
    following treatment:
    * The pair is removed from the buttons.
    * The label goes into the hint `x-fp6-inline-reply`. Only the server sets
      this hint; a client-sent copy is dropped.
    * `notification.canReply` becomes true.
    * The display time is 8 s instead of 5 s.
  * `x-kde-reply-placeholder-text` and `x-kde-reply-submit-button-text` are
    honoured.
  * `Notification.reply(text)` emits
    `org.freedesktop.Notifications.NotificationReplied(u id, s text)` (in the
    introspection XML, relayed by the adaptor) and then closes the
    notification. Empty replies are not sent.
  * `holdForReply(bool)` stops the bubble expiring while the user types.
  * **Parking**: when a replyable bubble times out, the notification stays
    open for its sender (no `NotificationClosed`), so the panel can reply
    later. It is closed when one of these happens:
    * the user replies;
    * the user dismisses its panel card (swipe, group ×, Clear all);
    * the sender closes or replaces it (a replacement shows a new bubble
      with the same id);
    * the sender leaves the bus;
    * more than 32 notifications are parked (the oldest is closed).
  * QML API on `Lomiri.Notifications.Model`: `fp6CanReply(id)`,
    `fp6Reply(id, text)`, `fp6Release(id)`, `fp6ParkNow(id)` and the signal
    `fp6ReplyableChanged()`.
* **Shell** (`lomiri-inline-reply.patch`, QML, generated by
  `test/mkpatch.sh` from `test/edit-inline-reply.py`):
  * Bubble (`Notification.qml`): a **Reply** button. Tapping it opens a
    field with **Send** and **×**. Return also sends.
  * Pulled-down panel (quick-settings' `QsNotifications.qml`, reached through
    `Panel.qml` and `ControlCentre.qml`): a **Reply** link on each card whose
    notification still accepts a reply. It opens an inline field. A card
    removes itself after a reply.
  * The cards keep the notification id (`nid`) and close parked
    notifications when they are dismissed (`Notifications.qml`).
  * Do Not Disturb "hide popups" parks a replyable bubble instead of closing
    it, so it can still be answered from the panel.

### Lock screen and privacy

* While the lock screen is up (`greeter.shown && greeter.locked`, as in
  quick settings), the reply field is **never** shown:
  * The button reads **Unlock to reply** and asks for the passcode
    (`greeter.notifyUserRequestedApp()`, as the panel's Unlock does).
  * The bubble is held while the passcode prompt is up. After the unlock the
    field opens.
  * If the passcode prompt is abandoned, the hold is released after 30 s.
* Locking while typing drops the draft.
* The content settings are unchanged. With "hide notification content while
  locked", bubbles show "New message" and cards show "Unlock to see the
  content". The reply affordance reveals nothing more than "Unlock to reply".
* Reply text is never stored: it lives in the text field until it is sent
  over D-Bus.

### KDE Connect (`../../kdeconnect`)

* A notification from a paired peer that carries `requestReplyId` (Android
  messaging apps) is shown with `inline-reply` and the placeholder "Reply to
  <app>".
* The daemon listens for `NotificationReplied`. It only accepts the signal
  from the owner of `org.freedesktop.Notifications`; a spoofed signal from
  another client is ignored (tested).
* It sends `kdeconnect.notification.reply {requestReplyId, message}`, once,
  and only while the peer's notifications toggle is on.
  `kdeconnect.notification.reply` was added to the advertised outgoing
  capabilities.
* **Not done:** the opposite direction (FP6 notifications forwarded to the
  peer do not offer a reply on the computer or phone). The daemon would need
  a way to inject a reply into another app's notification, and the server
  has no such API.

### Native apps

Any app that sends the `inline-reply` action works without changes. The
behaviour is the same as on KDE Plasma: `NotificationReplied` only, no
`ActionInvoked`. Telegram Desktop and KNotification-based apps check the
capability, so they switch to it on their own. GNOME's `GNotification` has no
inline replies, so Chatty/GTK apps keep their own UI.
`fp6-notify-reply` is the reference client.

### Not covered

* Notification history (Settings > Do Not Disturb > Notification history,
  fp6-notifyd): an on-disk log of past notifications, which have been closed
  by then. No reply there.
* Swiping a bubble away is still "dismiss": it closes the notification fully,
  as Lomiri always did. The panel card stays but offers no reply.
* `NotificationClosed` reasons are unchanged (Lomiri reports 1 for
  everything).

was 3600 (accessibility, edge-flash). Values already in use: 2000, 2100,
2200, 2300, 2400, 2500, 2600, 2700, 2800, 2900, 2950, 2960, 3000, 3100, 3200,
3300, 3400, 3500, 3600.

  * notifications (2900, DND in `Notifications.qml`/`Notification.qml`);
  * privacy-lock (2800, `Shell.qml`);
  * quick-settings (3100, installs `QsNotifications.qml` and
    `ControlCentre.qml`, edits `Panel.qml`);
  * edge-flash (3600, `Notification.qml`).

If their context moves, regenerate the shell patch:

```sh
nix-build test/patched-src.nix -o $SCRATCH/psrc        # target tree with this module off
test/mkpatch.sh $SCRATCH/psrc > lomiri-inline-reply.patch
```

## Test client

```sh
fp6-notify-reply --check            # "inline-reply: supported"
fp6-notify-reply                    # "Test Contact" / "Test message from +999 555 0100"
fp6-notify-reply --json --wait 300 --summary "Test Contact" --body "Hi" --placeholder "Reply to Test Contact"
```

It prints `replied (ID): TEXT` (or JSON). Exit status:

| Status | Meaning |
| --- | --- |
| 0 | replied |
| 1 | closed or default action, no reply |
| 2 | the server does not offer `inline-reply` |
| 3 | timed out (it then closes its notification) |
| 4 | bus or usage error |

It is installed in the system profile.

## Laptop verification (2026-10-28, no phone, no ARM builder)

* `nix-instantiate trial-lomiri-full-kernel6-fp6.nix -A config.system.build.toplevel`
  evaluates. `pkgs.lomiri.lomiri-notifications.patches` lists the app-name
  patch followed by the inline-reply patch.
* Both patches apply to the target's sources:
  * `spread-close-all/test/patched-src.nix`, which unpacks the full target's
    Lomiri with every patch and postPatch, builds with this patch applied.
  * `test/patched-src.nix` (module off) gives the tree that `mkpatch.sh`
    reproduces `lomiri-inline-reply.patch` from, byte for byte.
  * `qmllint` passes on all six patched QML files.
* `nix-build test` builds x86 lomiri-notifications with both patches and runs
  ctest verbosely:
  * `notificationtest` 46 passed, 1 skipped (upstream skip), including
    `testInlineReply`, `testInlineReplyParked` and `testInlineReplyHold`;
  * `notificationservertest` passes (the capability list includes
    `inline-reply`).
  * `fp6-notify-reply`: `cargo test` 4 passed, clippy clean.
* `test/e2e.sh $ENV`: a private session bus, the real x86 server in
  qmlscene, `fp6-notify-reply` as the client. All three rounds pass:
  * reply while the bubble is up;
  * reply after the bubble timed out (parked, no `NotificationClosed`
    first);
  * no reply (client times out).
* `test/run-tests.sh $ENV $PSRC OUT`: real patched shell QML offscreen with
  the real server, four synthetic notifications. 6/6 QML tests and 4/4
  clients pass:
  1. Locked: **Unlock to reply** asks for unlock; no field while locked; the
     bubble is held past 8 s. After the unlock the field opens; locking drops
     the draft; Send gets the reply to the client. The replied card loses its
     Reply.
  2. Hidden content while locked. The bubble expires and is parked. The panel
     card shows **Unlock to reply** while locked. After unlock the reply is
     sent from the panel and the card is removed.
  3. Expired, then Clear all: the client gets `NotificationClosed`.
  4. DND hides the bubble; it stays repliable.
* KDE Connect: `cargo test` gives 11 unit tests and 8 transport tests. The new
  tests are `reply_ids_and_packets` and `peer_notification_inline_reply`
  (synthetic Android notification → `inline-reply` action → server
  `NotificationReplied` → peer receives `kdeconnect.notification.reply`; a
  spoofed signal and a second reply are ignored; no action without
  `requestReplyId`).
* The previews and the log are in
